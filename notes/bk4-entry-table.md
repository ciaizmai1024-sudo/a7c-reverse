# BK4 设置镜像（/setting）条目表解析

## 结论先行

BK4 的“条目表”不是一张变长记录表，而是**两级索引**：

1. `0x10c` 起是 N 条**定长 6 字节**的条目描述符；
2. 每个描述符用 `count` 指向一段**连续的 6 字节字段描述符**；
3. 字段描述符用**文件绝对偏移** + `size` 指向内容区里的实际数据。

所以：

- 条目本身固定 6 字节，没有“每条 20 字节的条目”这种东西；
- 一个条目占用的索引字节数永远是 `6 × count`，一定是 6 的倍数；
- 真正可能正好 20 字节的是**字段**（`size == 20`），每份镜像各有 27 个；
- 这 27 个 20 字节字段里，**没有一个**是“机身全 0、出厂标准件有值”。出厂件 UC2 里同样的候选位置也是全 0，甚至机身件还在 entry 87/176 里多写了一点值。
- 因此：**如果固件验签用的公钥 SHA1（20 字节）确实存在，它不在这份 `/setting` 镜像里**（至少不是以本条表索引出的 `size=20` 明文字段形式）。详见第 9 节。

目录内的定位脚本：`bk4_find.py`（Python 3，只用标准库）。

## 2. 脚本用法

```bash
python3 bk4_find.py <镜像文件> <子命令> [参数...]
```

| 子命令 | 作用 |
|---|---|
| `info` | 打印头部、各区域边界、锚点、统计 |
| `list` | 列出条目；`--nonzero` 只看非空条目，`--type` / `--min-count` / `--max-count` 过滤 |
| `entry N` | 按**条目号**（0 起）打印该条目的全部字段；`--no-follow` 不读内容，`--raw` 直接 hexdump 索引窗口 |
| `find PATTERN` | 按**内容**定位：给出文件偏移、所在区域、所属字段/条目 |
| `field` | 列出字段；`--entry N`、`--size 20`、`--zero`、`--nonzero`、`--max-bytes` |
| `verify` | 校验结构不变量（魔数、边界、count 求和、锚点、目标范围等） |

`find` 的模式写法：

- `ascii:DIRECT-USE1` 或 `str:...`：按文本；
- `hex:00112233`：按十六进制；
- 去掉空格后是偶数长度、且全是十六进制字符时，自动按 hex 处理（可带 `0x` 前缀）；
- 其他情况按 UTF-8 文本。

常用示例（都在本目录实测过）：

```bash
# 总览
python3 bk4_find.py CX88600_UC2.bin info

# 只看有内容的条目
python3 bk4_find.py CX88600_UC2.bin list --nonzero

# 按条目号看 entry 87（包含 4 个 20 字节字段）
python3 bk4_find.py CX88600_UC2.bin entry 87

# 按内容定位：机身备份里的 DIRECT-USE1
python3 bk4_find.py BACKUP.BIN find ascii:DIRECT-USE1
#   -> hit at 0x1188a8
#      region: content area
#      -> field rec 29051, entry 316, target 0x1188a8, size 33, flags 0x0002

# 出厂件里的名字样文本
python3 bk4_find.py CX88600_UC2.bin find ascii:MODEL-NAME
#   -> field rec 23053, entry 261, target 0xbe5e4, size 16, flags 0x0001

# 枚举所有 20 字节字段（第 9 节的核心命令）
python3 bk4_find.py CX88600_UC2.bin field --size 20
python3 bk4_find.py BACKUP.BIN      field --size 20
python3 bk4_find.py CX88600_J1-203.bin field --size 20

# 结构自检
python3 bk4_find.py CX88600_UC2.bin verify
```

脚本按小端解析；表地址 `0x10C`、记录长度 6 等常量集中在文件开头，便于以后适配别的 BK4 变体。

## 3. 总体布局

以 `CX88600_UC2.bin` 为例（BIN/BAK 相同；J1 的地址见括号）：

```text
0x000000  头部（0x000..0x10B）
0x00010C  条目表       750 × 6 = 0x12A0 .. 0x143E (J1: 819 × 6)
0x0012A0  字段描述符数组 30064 × 6 = 0x12A0 .. 0x2D340 (J1: 0x143E .. 0x2D5A0)
0x02D340  内容区       0x2D340 .. 0x127828 = 文件尾 (J1: 0x2D5A0 .. 0x127E18)
0x127828  EOF
```

关键不变量（`verify` 全部通过，J1 有一条 WARN）：

- `content_off (0x18) + content_len (0x1C) == 文件大小`
- `0x10C + entry_count × 6 == 字段描述符数组起点`
- `sum(entry.count) == header[0x14]`
- `sum(entry.count)` 不超过描述符数组容量（J1 超出 2，见第 11 节）
- 最后两个条目的 `type=4`，其 `u24` 分别等于 `content_off` 和 `content_off+4`
- 所有 `size>0` 字段的 `target` 都落在内容区内（UC2: 28339/28339；J1: 28358/28358）

## 4. 头部字段

**[确认]** 以下偏移与含义由四份镜像交叉验证；标 **[推断]** 的只确认了数值/格式，语义未证实。

| 偏移 | 类型 | 含义 | UC2 / BIN / BAK / J1 |
|---|---|---|---|
| `0x00` | u32 | 物理地址 | `0x02E80000`（四份相同） |
| `0x04` | u32 | 标记 | `0xAAAAAAAA` |
| `0x08` | u32 | 模式 | 0=官方/标准件；1=机身备份 |
| `0x0C` | 4 bytes | 魔数 | `"BK4\0"` |
| `0x10` | u32 | 条目数 | 750 / 750 / 750 / 819 |
| `0x14` | u32 | 字段描述符总数（= Σcount） | 30063 / 30063 / 30063 / 30098 |
| `0x18` | u32 | 内容区文件偏移 | `0x2D340`（J1 `0x2D5A0`） |
| `0x1C` | u32 | 内容区长度 | `0xFA4E8`（J1 `0xFA878`） |
| `0x20` | u32 | 疑似校验/摘要，算法未解 | `0x07E2498D` / `0x073A1037` / `0x073A1702` / `0x07E3B075` |
| `0x24` | u32 | 常量 48，含义未解 | 四份都是 48 |
| `0x28` | u32 | 脏标志 **[推断]** | 0=标准件；1=机身备份 |
| `0x2C` | u32 | 备份槽/序号 **[推断]** | 0 / `0xB44` / `0xB45` / 0 |
| `0x38` | 8 bytes | 时间戳 **[确认格式]** | `u16 年, u8 月, u8 日, u8 时, u8 分, u8 秒, u8 填充` |
| `0x40` | ASCII，NUL 结尾 | 版本字符串（最长见 19 字符） | 见第 1 节 |
| `0xC0` | ASCII，NUL 结尾 | 设备名 | 见第 1 节 |
| `0x108` | u32 | 保留/未知（四份均为 0） | 0 |

时间戳格式的证据：

- UC2 `E5 07 0B 0F 03 27 3B 00` → 2021-11-15 03:39:59，版本串是 `2021111501`；
- J1 `EA 07 01 1F 03 0B 34 00` → 2026-01-31 03:11:52，版本串是 `2026013101`；
- BIN/BAK `E5 07 0B 0F 03 28 18 00` → 2021-11-15 03:40:24。

`0x20` 只是“看起来像校验和”：它随镜像内容变化，BIN/BAK 相差 265 字节时它也跟着变；算法未逆出。

## 5. 条目表：6 字节定长

**[确认]** 从 `0x10C` 开始，每条 6 字节，小端：

```c
struct Entry {          // 6 bytes
    uint16_t count;     // 该条目拥有多少个连续字段描述符
    uint24_t rec_start; // 字段描述符数组中的起始“记录号”
    uint8_t  type;      // 0=普通条目；4=内容锚点（u24 改为绝对地址）
};
```

**最容易踩的坑**：`rec_start` 是**记录下标**，不是字节偏移。早期把它当字节偏移会得到任意切割的“A/B 两段流”，那是错的。

已验证的原始字节示例：

```text
entry 0   @0x10C: 13 00 00 00 00 00   count=19,  rec_start=0,    type=0
entry 1   @0x112: 62 01 13 00 00 00   count=354, rec_start=19,   type=0
entry 87  @0x316: 41 00 28 0E 00 00   count=65,  rec_start=3624, type=0
entry 748 @0x1294: 00 00 40 D3 02 04   count=0,   u24=0x2D340,   type=4
entry 749 @0x129A: 00 00 44 D3 02 04   count=0,   u24=0x2D344,   type=4
```

由此可得：

- `sum(count) == 0x14`，四份镜像都成立；
- 表尾正好是字段描述符数组起点（750×6 = `0x12A0`）；
- 条目在表中的顺序就是它的序号（0..N-1）；表里没有单独的 id 字段；
- 空条目 = `count == 0` 的普通条目（UC2/机身 750 条里只有 186 条非空）；
- `type=4` 只在最后两条出现，不占字段描述符，`u24` 是内容区起始的两个 u32 锚点；
- 因为每个条目的索引占用是 `6 × count`，**不可能出现“20 字节的条目”**（20 不是 6 的倍数）。

`list` 会打印每个条目的记录范围、索引字节数、target 范围；`entry N` 会逐字段展开并跟随 target 读取内容。

## 6. 字段描述符数组

**[确认]** 紧跟在条目表后面，一条记录 6 字节：

```c
struct Record {         // 6 bytes
    uint16_t flags;     // 位图，语义未解
    uint24_t target;    // 内容区里的绝对文件偏移
    uint8_t  size;      // 该字段的字节数
};
```

字段顺序已验证（不是另一种“u24 target + u8 size + u16 flags”的排法）。反例：

```text
rec 29799 @0x2CD0A: 44 00 FC 66 12 14
  按 {u16 flags, u24 target, u8 size}: flags=0x0044, target=0x1266FC, size=20  -> 合法
  按 {u24 target, u8 size, u16 flags}: target=0xFC0044 在内容区外            -> 非法

rec 16856 @0x19DB0: 02 00 38 4B 0B 14
  按 {u16 flags, u24 target, u8 size}: flags=0x0002, target=0x0B4B38, size=20  -> 合法
  另一种：target=0x4B3802 在内容区外                                            -> 非法
```

要点：

- `target` 是**绝对文件偏移**，不是相对内容区的偏移；
- `size` 是字段字节数；观测到 70 种不同 size；
- `target=0xFFFFFF 且 size=255` 是**哨兵/空槽**（UC2 有 1721 个），表示该字段不存在；
- `size==255` 但 target 不是 `0xFFFFFF` 的字段有 **505** 个（四份镜像都是 505；UC2 的 2226 个 size=255 记录里另有 1721 个是哨兵），看起来是**变长/字符串块**，实际长度可能由数据内部或块类型决定 **[推断]**；
- `flags` 是位图（四份镜像都观测到 42 种取值：`0x0000, 0x0001, 0x0002, 0x0004, 0x0008, 0x000A, 0x0040, 0x0044, ... 0x00F8`），具体位义未解；
- UC2/BIN/BAK 的条目表和整个字段描述符数组**逐字节相同**（见第 10 节），所以三者的字段布局完全一致，只是内容区数据不同；
- 所有有效 target 都落在内容区内，但字段只直接引用内容区的约 **21.9%**（UC2：224,647 / 1,025,256 字节，5,583 段）；其余是块头、内部表、对齐/填充等未被条目直接引用的数据。因此不能把“内容区”简单等同于“所有字段首尾相接”。

## 7. 内容区

**[确认]** 内容区从 `content_off` 开始，以带标签的块组织：

- 起始 8 字节是 `02 00 00 00 01 00 00 00`，正好对应最后两个 `type=4` 锚点；
- 之后可见 `BIN!`、`FIN!`、`KEY!`、`PTN!`、`CNF!`、`IR3\x01` 等块标签；
- `KEY!` 块是一张 638 条 × 48 字节的表；
- 其余块的具体语义没有继续展开（不属于本次“条目表”的核心问题）。

**[推断]** `BIN!`/`FIN!` 等块内部还有自己的小结构（长度、子标签、ID），字段的 `target/size` 可以直接定位到这些块里的数据。

## 8. id 和名字在哪

### id

**[确认]** 条目号 = 条目表数组下标（0 起）。表里**没有**独立的 id 字段；`rec_start` 是累计记录号，`type=4` 的 u24 是内容地址，都不是 id。

因此“按条目号定位”就是 `python3 bk4_find.py IMAGE entry N`。

### 名字

**[确认]** 头部和条目表里没有明文名字字段，也没有名字指针；名字不可能直接从 6 字节描述符里读出来。

**[确认]** 部分条目内容里存在明文标识符，可以用 `find` 定位，例如：

- 机身备份：`DIRECT-USE1` @ `0x1188A8` → rec 29051，entry 316，size 33；
- 出厂 UC2：`MODEL-NAME` @ `0xBE5E4` → rec 23053，entry 261，size 16；
- 出厂 UC2：`PRODUCTCODE_SERIALNUMBER` @ `0xB2430` → rec 15479，entry 200，size 32；
- 内容区还能看到 `CHECK_CODE_II`、`CLIENT_VERSION`、`REGISTER`、`CAMSET01`、`FTPSET01` 等 ASCII token。

**[推断]** entry 1（`count=354, rec_start=19`）最像全局名称/界面字符串池：它指向一批 `size=255` 的块（起点 `0x2FB92`、`0x2FD96`、`0x2FF9A`、`0x3049E` ...），块里有大量重复的短 token 组，并且有一段明显的 0x66–0x7F 小字母表编码（26 个符号）、NUL 分隔的字符串。它可能是多语言 UI/菜单文本池。

**[未解]** 该编码方式没有破出来，所以目前**不能**把条目号和人类可读的名字做自动映射。能按“内容”找明文 token，不能按编码后的名字反查条目。

## 9. 20 字节与公钥 SHA1（重点）

### 9.1 “有没有长度正好 20 字节的条目？”

**[确认] 没有。** 条目描述符固定 6 字节；一个条目占用的索引是 `count × 6` 字节，永远是 6 的倍数。四份镜像里 `count == 20` 的条目数都是 0。

真正存在的是 **`size == 20` 的字段**：每份镜像 27 个。

### 9.2 27 个 20 字节字段的归属与跨镜像对比

命令：

```bash
python3 bk4_find.py CX88600_UC2.bin field --size 20
python3 bk4_find.py BACKUP.BIN      field --size 20
python3 bk4_find.py CX88600_J1-203.bin field --size 20
```

| owner entry | 个数 | UC2（出厂） | BACKUP.BIN/BAK（机身） |
|---|---:|---|---|
| 36 | 1 | 非零，结构化 | 相同 |
| 38 | 1 | 非零，结构化 | 相同 |
| 51 | 3 | 非零，结构化（其中 2 个相同） | 相同 |
| 87 | 4 | **全 0** | **非零**：`01 01…`、`01 01…`、`01 05…`、`07 01…` |
| 122 | 1 | 非零，结构化 | 相同 |
| 144 | 2 | 非零，结构化 | 相同 |
| 176 | 10 | **全 0** | 前 3 个非零：`30 00 00 00 00 10 00 00 03 00 00 00 12 56 57 13 01 00 00 00`、`20 …`、`10 …`；后 7 个仍为 0 |
| 215 | 1 | **全 0**（flags `0x0002`） | 全 0 |
| 292 | 2 | 非零，结构化 | 相同 |
| 368 | 1 | 非零，`01 C0 A8 7A …`（像 IP/网络参数） | 相同 |
| 658 | 1 | **全 0**（flags `0x0044`） | 全 0 |

统计：

- 出厂件 UC2：11 个非零 + 16 个全 0 = 27；
- 机身的 11 个非零字段与 UC2 **逐字节相同**；
- BIN 与 BAK 的 27 个字段**逐字节相同**；
- J1 的 27 个字段值与 UC2 **完全相同**，只是内容区整体后移 `0x260`，地址相应平移；
- 机身上唯一“比出厂多值”的是 entry 87 的 4 个和 entry 176 的前 3 个。

### 9.3 结论

**不存在“机身全 0、出厂标准件有值”的 20 字节字段。** 实际方向恰好相反：出厂件的候选位置（entry 87 / 176 / 215 / 658）全是 0，而机身件还在 entry 87/176 里写入了少量非零状态值。

如果你说的“机身里全 0 的这一项”是某个独立的 20 字节字段，那么最可能是 **entry 215**（flags `0x0002`，target `0xB4B38`）或 **entry 658**（flags `0x0044`，target `0x1266FC`）：它们在机身两份里全 0，在出厂 UC2/J1 里也仍然全 0——出厂标准件并没有把这一项填上值。

补充扫描（进一步排除“20 字节项被塞在更长字段里”）：

- 对每个 `size >= 20` 的字段，按任意起点滑动 20 字节窗口，与 BIN/BAK 对比，找“出厂非零 & 两份机身全 0”的窗口；
- 只命中 4 个明显模式化的区域：一段 `08 09 0A 0B …` 递增表、两处 ASCII `"0x00…"` 文本、一处平移的单字节 `01`；
- 没有一条像哈希（SHA1 应该是 20 个高熵字节）。
- 另外搜过 40–64 位十六进制文本：机身里有 3 条 64 字符的 SHA-256 风格串（`0x1187D4`、`0x118864`、`0x11AFA4`，属于设备配对数据），UC2/J1 里没有；没有 40 字符的 SHA1 十六进制串。

因此，对本目录这四份 `/setting` 镜像：

> **相机验签用的公钥 SHA1 不在这里。** 至少不是以“条目表索引出的 `size=20` 字段”或“明文 40 位 hex”的形式存在。

**[推断]** 它更可能在 bootloader / 安全区 / 其他分区，或以加密/封装形式存在；也可能长度不是 20（例如带 padding 的 32 字节结构）。本次没有对全文件做“任意 20 字节高熵窗口”的密码学级排查，只对条目表能索引到的字段和显而易见的 hex 文本做了穷举。

## 10. 镜像之间的差异

### UC2 vs 机身（BACKUP.BIN）

- 总差异 99,401 字节：
  - 头部 14 字节（`0x08` 模式、`0x20` 校验、`0x28` 脏标志、`0x2C` 备份槽、`0x3D` 时间戳秒、`0xC0` 设备名）；
  - 条目表：**0 字节**；
  - 字段描述符数组：**0 字节**；
  - 内容区：99,387 字节。
- 也就是说，**两者的条目结构和字段布局逐字节相同**，差异只是“设置值”本身。

### BACKUP.BIN vs BACKUP.BAK

- 265 字节不同，分成 85 个连续小段；
- 头部：`0x20` 校验（`0x073A1037` vs `0x073A1702`）、`0x2C` 备份槽（`0xB44` vs `0xB45`）；
- 内容区集中在 `0x4B6B2`、`0x61540`、`0x66980–0x6A549`、`0x89762–0x8988E`、`0xB468C`、`0xC1651–0xC16DC`、`0x11C121` 等小片，像运行期状态/计数/校准值；
- **27 个 20 字节字段在两份机身拷贝中逐字节相同**；
- 没有出现“机身全 0 / 出厂有值”的 20 字节项。

## 11. 已确认 / 推断 / 未解

### 已确认（脚本 + 四份镜像交叉验证）

- 头部各字段偏移与大小；`content_off + content_len == 文件大小`。
- 条目表从 `0x10C` 开始，6 字节 `{u16 count, u24 rec_start, u8 type}`。
- `rec_start` 是记录号；`sum(count) == 0x14`；表尾 = 字段数组起点。
- 字段 6 字节 `{u16 flags, u24 target, u8 size}`；target 是绝对文件偏移。
- 哨兵 `target=0xFFFFFF & size=255`；`size` 是字段字节数。
- 最后两个 `type=4` 条目锚定 `content_off` / `content_off+4`。
- 27 个 `size=20` 字段的归属、取值、跨镜像对比。
- 不存在“机身全 0、出厂有值”的 20 字节字段。
- 头部时间戳格式（与版本串日期吻合）。
- UC2 与机身件的表/字段数组逐字节相同；BIN/BAK 的 20 字节字段相同。

### 推断

- 条目号就是 id；表里没有名字字段。
- entry 1 是名称/界面字符串池；`0x66–0x7F` 是某种小字母表编码。
- `size=255` 是变长/字符串块。
- `flags` 是位图；`0x28` 是脏标志；`0x2C` 是备份槽/序号。
- 公钥 SHA1 在 bootloader/安全区/加密区，而不是本镜像。

### 未解

- entry 1 字符串池的编码/压缩算法（目前无法按名字反查条目）。
- `flags` 各 bit 的含义（42 种取值）。
- `0x20` 校验和算法。
- `0x24=48`、`0x2C` 的精确语义、`0x108` 的用途。
- 内容区 `BIN!`/`FIN!`/`KEY!`/`PTN!`/`CNF!`/`IR3` 块的完整语义与 ID 体系。
- J1 表尾异常：`sum(count)=30098`，但字段数组容量只有 30096 条；最后一条普通 entry 727（`count=2, rec_start=30096`）跨过数组边界，读到了内容区开头的 `02 00 00 00 01 00 00 00`，解析出 target `0x000200 / 0x000000`、size 0 的两条“字段”。`verify` 对此只报 WARN，不影响其余结构判断。这可能是该版本固件的一个 off-by-2，也可能是表尾还有未识别的特殊项。
- 公钥 SHA1 的真实存放位置与形式。
